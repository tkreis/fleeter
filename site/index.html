Your Macs, Linux boxes and containers, run as one fleet of coding agents.

fleeter is one bash tool. Your laptop is the master: it enrols machines over Tailscale with single-use invites, pushes Claude Code, Codex, Cursor, Grok, a browser with MCP servers, your instructions, skills and secrets over SSH, and can kick any node out. Nodes keep working while the master is off and share one Markdown memory.

Read the quickstart Read the architecture

Get started on your laptop 
$ curl -fsSL https://tkreis.github.io/fleeter/install.sh | bash
$ fleet init master

What you get on every node

  • Agents installed and logged in

    Claude Code, Codex CLI, Cursor CLI and Grok Build, kept current by their own updaters. Logins reuse what the master has wherever the vendor allows; otherwise fleet login runs the device-code flow on the node.

  • A browser the agents can drive

    Chrome or chromium plus chrome-devtools-mcp and @playwright/mcp at pinned versions, behind wrappers that run headless on servers. Runtimes via mise, pnpm, uv, gh, Docker; optional CLIProxyAPI and T3 Code.

  • The same instructions and skills

    One AGENTS.md in your private config repo, rendered into the Claude, Codex, Cursor and Grok locations. Skills and harness templates are captured from the master with fleet config publish and pulled by every node.

  • Secrets from an encrypted vault

    Secrets live in an encrypted vault on the master (age, key in your macOS Keychain). They're decrypted only in memory while being sent to a node over SSH, and land in a file only your user can read. Two profiles: minimal for throwaway containers, full for your own machines.

  • Updates when your master is on

    The master pushes new tools, skills, config and secrets whenever it is on: fleet sync runs on a schedule. Nodes keep working with what they have while it is off. Nodes can be Macs, Linux boxes or containers.

  • An agent that can run the fleet

    fleet skill install puts a SKILL.md on the master, so a coding agent there can check nodes, run commands on them and push updates for you, within the same confirmations as you.

How it works

Three git repos and one vault. The master pushes over OpenSSH inside your tailnet with its own key and pinned host keys; fleet sync does that on a schedule whenever the master is on. Nodes fetch code, config and memory themselves with per-node deploy keys, so they keep working while the master is off.

Joining a machine

An invite is good for one machine and one hour. The master finds the new machine and finishes the setup on its own.

  1. on the master

    Mint an invite

    fleet invite --name mini prints one command and an invite code.

  2. on the new machine

    Paste the command

    Paste it into a terminal and enter the invite code when asked.

  3. on the master, a few minutes later

    It sets itself up

    The master pushes tools, instructions, skills and secrets; fleet list shows the machine as provisioned.

Shared memory

Optional, and worth it. A plain Markdown vault, Obsidian-compatible, in a private git repo. Every harness reads and writes files natively; git works headless and offline and keeps the history.

Each node commits only inside nodes/<name>/, its own folder, so every node's writes stay separate. Each node pulls the whole vault, so a fact learned on one machine is on every other within two sync cycles. INDEX.md, one line per note, is rebuilt by a GitHub Action on every push and read first.

The global instructions tell every agent to read nodes/** as reference material. What you promote into notes/ is reviewed by you, on the master.

Security model

Assume a node can be fully compromised: an agent there runs untrusted code and reads untrusted content all day. The design makes that node cheap to lose.

  • Push only, from the master. The master connects to nodes over OpenSSH with its own key and pinned host keys. Every change flows from the master outward, including enrolment.
  • Nodes are isolated on the tailnet. Each node carries tag:fleet-node, and your own devices may reach it on port 22. fleet doctor checks the live policy and probes from the nodes themselves.
  • Invites are single use. One pre-authorised Tailscale key, good for one machine and one hour, claimed by the master exactly once. The code is read from a hidden prompt.
  • Every node has its own keys. Its own Tailscale device and its own deploy keys: code and config read-only, memory writable inside its own folder. fleet kick revokes all of them together and lists the secrets that node held, so you know what to rotate.
  • Secrets live in an encrypted vault on the master (age, key in your macOS Keychain). They're decrypted only in memory while being sent to a node over SSH, and land in a file only your user can read. The vault stays outside git, and fleet config publish scans for secrets before every push.

The full threat model, the mechanisms table and the rotation checklist are in docs/SECURITY.md.

CommandWhat it does
On the master
fleet init master --config-dir DIRPreflight, vault and keys, tailnet policy merge, sync schedule. Idempotent.
fleet invite --name N [--user U] [--ephemeral]Single-use join one-liner and invite code, valid one hour.
fleet list [--json]Every node in one table: online, state, synced, last provision, tools, memory, proxy, version.
fleet syncPull the master's repos, enrol new machines, push updates to every node. Runs on a schedule.
fleet ssh NODE [CMD]Shell on a node, or run a command there with its fleet environment loaded.
fleet secrets set NAME [--profile P]Store a secret from a hidden prompt or stdin. secrets list shows names only.
fleet config publishCapture harness and skills from the master, secret scan, commit, push.
fleet skill installInstall the fleet agent skill (SKILL.md) on the master.
fleet kick NODERevoke: stop jobs, delete the device and deploy keys, list secrets to rotate.
fleet doctorVault, tokens, policy, GitHub access, schedule, and an isolation probe from every node.
On a node
fleet status [--json]Versions, logins, revisions, memory state, token ages.
fleet login [TOOL]Device-code login for a tool whose status is login.

Every command and flag, including provision, files, proxy, policy, t3 and leave, is in the README command reference.
